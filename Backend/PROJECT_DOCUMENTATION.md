# وثيقة توثيق الباك إند

## نظام إدارة المؤسسات التعليمية

## 1. مقدمة

يتناول هذا المستند الجزء الخلفي (Backend) من نظام إدارة المؤسسات التعليمية. يوفر هذا الجزء واجهة برمجية REST API تربط واجهة المستخدم بقاعدة البيانات، وتدير بيانات المستخدمين والأدوار الأكاديمية، والدفعات والمقررات والجلسات، والحضور والنتائج والملاحظات.

صُممت الوظائف لتخدم أربعة أدوار رئيسية: المدير، والسكرتير، والمدرس، والطالب. ويملك كل دور مجموعة عمليات تناسب مسؤولياته، مع حماية المسارات التي تتطلب تسجيل الدخول والتحقق من صلاحية الدور.

## 2. أهداف الباك إند

- تنظيم بيانات المؤسسة التعليمية وتوفير مصدر موحد لها.
- إتاحة وظائف النظام عبر مسارات API واضحة وقابلة للاستهلاك من الواجهة الأمامية.
- الفصل بين استقبال طلبات HTTP ومنطق الأعمال والوصول إلى قاعدة البيانات.
- تنظيم الصلاحيات وفق أدوار المستخدمين.
- دعم متابعة تسجيل الطلاب، والجلسات، والحضور، والنتائج.
- توفير مؤشرات وتقارير تساعد الإدارة على متابعة سير العمل.

## 3. التقنيات المستخدمة

| التقنية | الاستخدام |
|---|---|
| Node.js | تشغيل بيئة JavaScript على الخادم. |
| Express | إنشاء الخادم وتعريف مسارات REST API. |
| MongoDB | تخزين بيانات النظام بصيغة مستندات. |
| Mongoose | تعريف مخططات البيانات والعلاقات والاستعلامات. |
| JSON Web Token (JWT) | تمثيل هوية المستخدم في الطلبات المحمية. |
| bcryptjs | تجزئة كلمات المرور والتحقق منها عند تسجيل الدخول. |
| Zod | التحقق من صحة أجسام الطلبات في المسارات التي تستخدم مخططات التحقق. |
| dotenv | تحميل إعدادات التشغيل من متغيرات البيئة. |
| CORS | السماح للواجهة الأمامية بطلب خدمات الخادم وفق إعدادات CORS المستخدمة. |

## 4. مزايا النظام بحسب الدور

### 4.1 المدير

يمتلك المدير واجهة إدارة شاملة عبر `/api/admin`، وتتضمن:

1. **لوحة الإحصاءات**
   - عدد الطلاب والطلاب النشطين والمدرسين.
   - عدد الدفعات والدفعات النشطة والجلسات.
   - عدد الاعتمادات المعلّقة.
   - متوسط النتائج ومعدل الحضور الإجمالي.

2. **النشاط**
   - عرض أحدث الجلسات ومعلوماتها الأساسية مثل الدفعة والتاريخ والموضوع والحالة.

3. **إدارة المستخدمين**
   - عرض المستخدمين مع إمكانات البحث والتصفية والترقيم.
   - إنشاء حسابات وتعديل بياناتها.
   - عرض تفاصيل مستخدم.
   - تفعيل الحساب أو تعطيله.
   - أرشفة المستخدم بدل حذفه فعليًا.

4. **الاعتمادات**
   - استعراض العناصر غير النشطة بانتظار المراجعة.
   - اعتماد عناصر من مجموعات المستخدمين والمقررات والمستويات والدفعات والنتائج.
   - رفض العناصر وفق السلوك المطبق لكل نوع.

5. **التقارير**
   - عرض مؤشرات عامة للنظام.
   - عرض تقرير دفعة يتضمن عدد الطلاب والجلسات ومتوسط النتائج والحضور وملخص الطلاب.
   - تصدير التقرير العام بصيغتي JSON وCSV.

6. **إدارة الدفعات**
   - إنشاء الدفعات واستعراضها وتعديلها وأرشفتها.
   - عرض الطلاب المسجلين في دفعة.
   - ربط الدفعة بمستوى ومدرس وتواريخ وسعة وحالة.

7. **إدارة المقررات والمستويات**
   - إنشاء المقررات وتعديلها واستعراضها وأرشفتها.
   - إنشاء المستويات وربطها بمقرر وترتيبها، ثم تعديلها واستعراضها وأرشفتها.

### 4.2 السكرتير

تغطي واجهة السكرتير `/api/secretary` العمليات الإدارية اليومية:

1. **لوحة المعلومات**
   - ملخص أعداد الطلاب الجدد والمدرسين والدفعات النشطة والجلسات والملاحظات والاعتمادات المعلّقة.

2. **شؤون الطلاب**
   - إنشاء حسابات الطلاب، واستعراض القائمة والتفاصيل، وتحديث البيانات وأرشفة الحساب.
   - عرض الطلاب غير المسجلين في دفعة محددة لتسهيل إضافتهم إليها.

3. **إدارة المدرسين**
   - إنشاء حسابات المدرسين واستعراضهم وتحديث بياناتهم وأرشفتهم.

4. **إدارة الدفعات**
   - إنشاء الدفعات واستعراضها وتعديلها وأرشفتها.
   - عرض تسجيلات الطلاب ضمن كل دفعة.

5. **تسجيل الطلاب**
   - إنشاء تسجيل طالب في دفعة.
   - تحديث حالة التسجيل إلى نشط أو منسحب أو مكتمل.
   - التحقق من وجود الطالب والدفعة، ومنع التسجيل النشط المكرر، ومراعاة سعة الدفعة وفق منطق الخدمة.

6. **المقررات والمستويات**
   - استعراض المقررات والمستويات وإنشاؤها وتعديلها وأرشفتها.

7. **ملاحظات الطلاب**
   - إنشاء ملاحظة لطالب، واستعراض الملاحظات وتفاصيلها وتعديلها وأرشفتها.
   - تحديد مستوى ظهور الملاحظة، مثل ظهورها للطالب أو اقتصارها على جهات أخرى بحسب قيمة الرؤية المسجلة.

### 4.3 المدرس

تتيح واجهة المدرس `/api/teacher` متابعة الدفعات المسندة إليه والطلاب المرتبطين بها:

1. **لوحة المدرس**
   - عرض عدد الدفعات والطلاب والجلسات القادمة ومتوسط النتائج والحضور والنتائج المعلّقة.
   - عرض الدفعات المسندة للمدرس ومؤشرات كل دفعة.
   - استعراض الجلسات القادمة.

2. **إدارة الجلسات**
   - استعراض جلسات المدرس وإضافة جلسة وتحديثها وحذفها.
   - تسجيل رقم الجلسة وتاريخها وموضوعها وحالتها.
   - التحقق من ارتباط الجلسة بدفعة يملكها المدرس.

3. **الحضور**
   - تسجيل حضور الطالب أو تحديث حالته لجلسة.
   - الحالات المدعومة: حاضر (`present`)، غائب (`absent`)، متأخر (`late`)، بعذر (`excused`).
   - عرض الحضور المسجل لجلسة وملخص الغياب.
   - التحقق من أن تسجيل الطالب مرتبط بدفعة الجلسة.

4. **النتائج**
   - إضافة نتيجة إلى تسجيل طالب، مع نوع النتيجة والدرجة والدرجة القصوى والتقدير والملاحظات.
   - استعراض النتائج وتعديلها وأرشفتها.
   - اعتماد النتائج غير النشطة لجميع تسجيلات دفعة يملكها المدرس.
   - التحقق من ارتباط التسجيل والنتيجة بدفعات المدرس.

5. **متابعة الطلاب**
   - عرض الطلاب المسجلين في دفعات المدرس.
   - إظهار متوسط النتائج ومعدل الحضور لكل تسجيل، إلى جانب بيانات الطالب الأساسية.

### 4.4 الطالب

توفر واجهة الطالب `/api/student` عرضًا للبيانات الأكاديمية المرتبطة بحسابه:

1. **الملف الشخصي:** الاسم والبريد والهاتف والدراسة وتاريخ الميلاد وعدد التسجيلات ومتوسط النتائج والحضور.
2. **دفعاتي:** الدفعات المسجل فيها، والمستوى والمدرس، وعدد الجلسات المنجزة والإجمالية، ومتوسط النتائج والحضور، وموعد الجلسة القادمة إن وجدت.
3. **درجاتي:** النتائج المسجلة مع نوع النتيجة والدرجة والدرجة القصوى والتقدير والملاحظات والتاريخ.
4. **حضوري:** سجلات الحضور وحالة الطالب وتفاصيل الجلسة والدفعة.
5. **ملاحظاتي:** الملاحظات المسموح بعرضها للطالب وفق قيمة الرؤية المسجلة.

## 5. مسارات API الرئيسية

جميع المسارات تحت البادئة `/api`. تتطلب مجموعات المدير والسكرتير والمدرس والطالب مصادقة مناسبة للدور، باستثناء مسارات المصادقة العامة.

| المجموعة | المسارات الرئيسية |
|---|---|
| المصادقة `/api/auth` | `POST /register`، `POST /login`، `GET /me` |
| المدير `/api/admin` | `/stats`، `/activity`، `/users`، `/approvals`، `/reports`، `/cohorts`، `/courses`، `/levels` |
| السكرتير `/api/secretary` | `/stats`، `/students`، `/teachers`، `/cohorts`، `/enrollments`، `/courses`، `/levels`، `/notes` |
| المدرس `/api/teacher` | `/stats`، `/cohorts`، `/sessions`، `/attendance`، `/results`، `/students` |
| الطالب `/api/student` | `/me`، `/cohorts`، `/grades`، `/attendance`، `/notes` |

تُرسل بيانات معظم عمليات الإنشاء والتعديل بصيغة JSON. وتُرسل رموز JWT للمسارات المحمية في الترويسة:

```http
Authorization: Bearer <token>
```

## 6. بنية البيانات والعلاقات

تُخزن البيانات في MongoDB، وتصف مخططات Mongoose الحقول والروابط الرئيسية:

| الكيان | الغرض والعلاقات الأساسية |
|---|---|
| المستخدم `User` | بيانات الدخول والاسم والدور ومعلومات الطالب أو المدرس وحالة التفعيل. |
| المقرر `Course` | اسم المقرر ووصفه وحالته. |
| المستوى `Level` | مستوى ضمن مقرر، مع رقم ترتيب. |
| الدفعة `Cohort` | رمز الدفعة وتواريخها وسعتها وحالتها، وترتبط بمستوى ومدرس. |
| التسجيل `Enrollment` | يربط طالبًا بدفعة ويحتفظ بحالة التسجيل وتاريخه. |
| الجلسة `Session` | جلسة تابعة لدفعة، مع التاريخ والرقم والموضوع والحالة. |
| الحضور `Attendance` | حالة حضور تسجيل طالب في جلسة. |
| النتيجة `EnrollmentResult` | نتيجة مرتبطة بتسجيل، مع درجة ودرجة قصوى وتقدير وملاحظات وحالة اعتماد. |
| ملاحظة الطالب `StudentNote` | ملاحظة مرتبطة بطالب ومدرس مع مستوى للرؤية. |

تستخدم عدة نماذج حقولًا زمنية للإنشاء والتحديث، وتستخدم سجلات مثل المستخدمين والدفعات والمقررات والمستويات والنتائج والملاحظات حقل `deletedAt` للأرشفة المنطقية. أما حذف الجلسة فيتم حاليًا بالحذف الفعلي.

## 7. البنية البرمجية

يتبع الباك إند فصلًا بين المسؤوليات:

1. **`server.js`:** نقطة تشغيل الخادم وطلب الاتصال بقاعدة البيانات.
2. **`app.js`:** تهيئة Express وربط مجموعات المسارات وإعداد JSON وCORS.
3. **`routers/`:** تعريف المسارات وربطها بالتحقق والمصادقة والمتحكمات.
4. **`middleware/`:** التحقق من JWT والدور والتحقق من بيانات الطلب.
5. **`controllers/`:** تنسيق طلب HTTP واستدعاء الخدمة وإرجاع الاستجابة.
6. **`services/`:** تنفيذ منطق الأعمال والاستعلامات والتحديثات.
7. **`models/`:** مخططات MongoDB وعلاقات المستندات.
8. **`validators/`:** مخططات Zod لمدخلات المسارات.
9. **`seed/`:** سكربت البيانات الأولية وسكربت فحص المسارات.

## 8. المصادقة والتحقق والاستجابات

- تستخدم المصادقة رموز JWT الموقعة بسر من إعدادات البيئة.
- تتحقق المسارات المحمية من هوية الحساب ودوره قبل تنفيذ العملية.
- تُجزّأ كلمات المرور باستخدام `bcryptjs` ولا تُخزن كنص صريح.
- تُطبق مخططات Zod على مسارات الإنشاء والتعديل المحددة في ملفات المسارات.
- تستخدم كثير من الاستجابات غلافًا يتضمن `success` و`data`، وتختلف بعض الاستجابات بحسب المسار.
- تعيد المسارات غير المعروفة حالة `404`.

## 9. التشغيل والإعداد

### المتطلبات

- Node.js 18 أو أحدث.
- npm.
- MongoDB محلية أو مستضافة.

### إعداد متغيرات البيئة

من مجلد `Backend`:

```powershell
npm install
Copy-Item .env.example .env
```

ثم تعبئة ملف `.env`:

```dotenv
PORT=4000
DB_URI=mongodb://127.0.0.1:27017/educational_institution
JWT_SECRET=ضع_قيمة_سرية_طويلة_وعشوائية
JWT_EXPIRES_IN=1d
```

يجب عدم حفظ أسرار التشغيل أو بيانات الاتصال الحقيقية في المستودع.

### تشغيل الخادم

```powershell
npm run dev
```

أو للتشغيل العادي:

```powershell
npm start
```

العنوان الافتراضي هو `http://localhost:4000` ما لم يتم تغيير `PORT`.

## 10. البيانات الأولية وفحص المسارات

### إدخال البيانات الأولية

```powershell
npm run seed
```

> **تنبيه مهم:** سكربت `seed/seeder.js` الحالي يحذف بيانات مجموعات النظام قبل إدخال بياناته. يجب تشغيله فقط على قاعدة تطوير/اختبار وبعد التأكد من عدم الحاجة إلى البيانات الحالية.

### فحص مسارات API

بعد تشغيل الخادم وضبط قاعدة البيانات، يمكن تشغيل الفاحص:

```powershell
$env:ROUTE_CHECK_CONFIRM = "YES"
npm run check:routes
```

ينشئ الفاحص بيانات اختبار بأسماء مميزة، ويجرب طلبات المجموعات المختلفة، ويترك بيانات الاختبار في قاعدة البيانات. بعض الطلبات تعدّل سجلات الاختبار التي أنشأها الفاحص، ولا يحذف أي سجل. يوصى باستخدام قاعدة اختبار مخصصة.

## 11. حدود التنفيذ الحالية

توضح النقاط التالية ما هو مطبق حاليًا لتجنب اعتبار وظائف مستقبلية جزءًا من النسخة الحالية:

- لا يوجد مسار API مفعّل لتسجيل الخروج؛ تسجيل الخروج يتطلب من العميل التخلص من الرمز.
- تختلف استجابات الأخطاء وتنسيقاتها بين بعض المسارات، لذا قد لا تكون موحدة بالكامل.
- الحذف الفعلي للجلسات يختلف عن الأرشفة المنطقية المستخدمة في عدد من الكيانات الأخرى.
- يدعم النظام التصدير الحالي للتقرير العام بصيغة JSON أو CSV؛ لا يُقصد بذلك وجود تصدير لكل أنواع البيانات.
- يجب مراجعة إعدادات النشر والأمان وقواعد قاعدة البيانات قبل استخدام النظام في بيئة إنتاجية.

## 12. الخلاصة

يشكل الباك إند طبقة الخدمات والبيانات لنظام إدارة المؤسسات التعليمية. ويغطي الوظائف الأساسية لإدارة الحسابات والأدوار، والدفعات والمقررات، والتسجيلات، والجلسات، والحضور، والنتائج، والملاحظات، إضافة إلى لوحات المؤشرات والتقارير. كما يتيح تقسيم البنية إلى مسارات ومتحكمات وخدمات ونماذج تطوير النظام وصيانته بصورة منظمة.
